# P7 — Tools in their own repositories ("tool sources")

**Goal.** Tools leave the base repository for `smith-lab/lab-tools` (D1, private). The base loads tools
from any number of git repositories, each with its own branch choice, update button and safety rules for public
repositories (D2). Plan: §9.

**Before you start:** P1 and P4 merged. The owner has created the empty private repository
`smith-lab/lab-tools` and added it to the server token's repository list (Contents: Read). An agent can
only use `add_repo` once the repository exists.

## Tasks

- [x] **7.1 Tool sources in the base: `mister_plis/toolsources.py`.**
  - `<data_dir>/tool_sources.json` holds a list of `{name, url, branch, enabled, pinned, trusted}`. It can be
    preset from `config.toml` as a `[[tool_sources]]` array; on first start it is preset with the lab
    repository.
  - Each source is cloned to `<app home>/tool-sources/<name>/` with `gitutil`. **Untrusted sources never get the
    token**: run git with an empty credential helper.
  - Check, update, branch switching and pinning reuse the logic in `updater.py`. Factor out a shared
    `GitCheckout` class that both the base and tool sources use: fast-forward only, refuses local edits, lists
    incoming commits.
  - *Check:* tests with local bare repos as sources: add, switch branch, pin, update, refuse a dirty checkout,
    remove.
- [x] **7.2 The manifest `mister-plis-tools.toml`:** name, title, `requires_toolkit`, requirements, locale. Read
  and validate it; an unsupported `requires_toolkit` marks the whole source broken with a clear message.
- [x] **7.3 Registry loading from sources.**
  - Each enabled source is imported as the package `mp_tools_<name>` (importlib with
    `submodule_search_locations`), so helper modules never collide.
  - Every tool is tagged with `source` and the commit.
  - The first source in the list wins a tool id; later duplicates are listed as broken.
  - Each source's `locale` file is merged into the catalogue; the base's own strings win.
  - `__main__.py --reload` watches the source folders too.
  - The `job.json` `tool.source` and `tool.commit` are now real values.
  - *Check:* tests with two fixture sources that share a helper name and collide on one id.
- [x] **7.4 Dependencies.**
  - The base gains `constraints.txt` (exact versions of its own dependencies; add a script that regenerates it).
  - Before installing a source's `requirements.txt`, run
    `pip install --dry-run --report - -r … -c constraints.txt`. If anything the base pins would change, stop
    and show the packages. Otherwise install.
  - A restart is scheduled as for base updates (wait for idle, confirm if jobs run).
- [x] **7.5 Public repositories (D2).**
  - Adding a source shows its URL, manifest, requirements and file list.
  - A non-trusted source is saved **disabled and pinned** to the shown commit.
  - Enabling it is a separate, explicit click.
  - Updating a pinned source shows the incoming commits and changed files before moving the pin.
  - *Check:* API tests of the whole flow.
- [x] **7.6 The Tool sources panel** on System & updates: list, add, enable/disable, check, update, run another
  branch, pin/unpin, remove; last error per source; Polish strings.
- [x] **7.7 A job whose tool is gone** (source removed or disabled) still opens, prints and backs up from
  `job.json`; only Re-run is disabled, with the source named.
- [x] **7.8 Create `MISTER_PLIS-tools`.**
  - On a fresh clone, run `git filter-repo --path tools/ --path-rename tools/:`, so history is kept.
  - Add `mister-plis-tools.toml`, `requirements.txt` with the tool-only packages (`scikit-image`, `trimesh`,
    `fast-simplification`, `pypdfium2`, `pillow-heif`, `pyobjc-framework-Vision`), a README (the old
    `ADDING_TOOLS.md` howto), and a CI workflow that installs the base from git at `main` and runs `tests/`.
  - Push to the new repository. This is the only step that writes to another repository: confirm with the owner
    first.
- [x] **7.9 Remove `tools/` from the base.**
  - Add `tests/fixtures/toolsource/` with two toy tools for the base's tests.
  - Remove the tool-only packages from the base's `requirements.txt`.
  - `docs/ADDING_TOOLS.md` keeps the SDK reference and points to the tools repository for the howto.
- [x] **7.10 Deploy notes.** `docs/DEPLOY_MAC_STUDIO.md` adds the token scope for `MISTER_PLIS-tools`, the Tool
  sources panel and the first start (the server clones the lab source by itself). The Mac launcher needs no
  change.

## Done when

- the base with no sources starts and says "no tools yet";
- with the lab source on `main`, every tool is back, old jobs open and re-run, and the whole suite and the
  tools repository's CI are green;
- switching the lab source to a test branch and back works on the Mac Studio;
- a public test source can be added, reviewed, enabled, updated through review, and removed;
- a package conflict is caught before installing.

## Rollback

Switch the base to the previous release branch: it still has `tools/` in its history. The tools repository can
stay; it does no harm.
