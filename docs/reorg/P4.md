# P4 — Module framework, and Time Machine in `modules/timemachine`

**Goal.** The base gets a documented module interface and hooks. Time Machine moves, unchanged in behaviour,
into `modules/timemachine/`, and the base no longer names it anywhere. Plan: §7.

**Before you start:** P2 and P3 merged.

Work in two halves, each mergeable on its own:

- **(A)** add the framework and the hooks while Time Machine still lives in the base, wiring Time Machine through
  the hooks;
- **(B)** move the files.

## Half A — framework and hooks

- [x] **4.1 `mister_plis/modules.py`.**
  - The dataclasses `Module`, `NavItem`, `Hooks` and `ModuleContext`, as in plan §7.2, with the shell
    contributions added for P6 (`shell = {"topbar", "aside", "head_script", "scripts"}`, `hide_panels`).
  - A `load_modules(app, enabled)` loader:
    - imports `modules.<id>`, checks `api == 1`, calls `setup(ctx)` then `register(app, ctx)`;
    - starts `threads`;
    - adds `templates` to the Jinja loader as `<id>/…`;
    - mounts `static` at `/m/<id>/static`;
    - merges `locale`;
    - records failures in `registry.broken`, like tools.
  - The setting is `modules = [...]` in `config.toml`; default: every folder in `modules/`.
  - *Check:* unit tests with a toy module in `tests/fixtures/modules/hello/`, covering a route, a nav item, a
    thread, a panel and a failing module.
- [x] **4.2 `ModuleContext` services.**
  - `storage`, `data` and `settings` (the `[modules.<id>]` table);
  - `jobs` (`JobStore`) and `backups` (`BackupCatalogue` + settings);
  - `people` (`canonical`), `page`, `tr`, `printer`;
  - `git` (temporarily the existing `updater.git` wrapper; P5 replaces it with `gitutil`).
- [x] **4.3 Generic shell.**
  - `base.html` draws the sidebar's module links from `nav`.
  - System and Settings include `panels["system"]` / `panels["settings"]` in a loop.
  - Per-page module scripts are added from `scripts[page_kind]`.
  - `page(..., shell_class=…)` replaces `tm_mode`.
  - `app.js` gets `MP.hooks = {resultActions: [], jobFilters: []}`, and `jobs.js` draws the declared filters.
  - *Check:* the visual result is unchanged. Compare screenshots of Home, a tool page, Jobs, System and Settings
    before and after (`run` skill / Playwright).
- [x] **4.4 Hooks wired.** Replace each hard-coded call to Time Machine in `app.py`:
  - `job_flags` (for `in_tm`/`tm_root`);
  - `people` and `rename_person`;
  - `file_resolver` (for `/api/tm/{id}/files/` in the PDF);
  - the "Add to Time Machine" button through `MP.hooks.resultActions`;
  - the "kept" filter through `jobFilters`.

  Index rows get `modules.timemachine.kept`.
  *Check:* `tests/test_timemachine.py` green unchanged.
- [x] **4.5 The job-number mark** stays in the base `report.py`. Rename it to "job mark" in code and comments,
  so nothing implies Time Machine.

## Half B — the move

- [x] **4.6 Create `modules/timemachine/`** (`__init__.py` with `module = Module(...)`, `service.py` ← `timemachine.py`,
  `history.py` ← `tmgit.py`, `web.py` ← the `/timemachine` and `/api/tm/*` routes from `app.py`, `templates/`
  (`timemachine.html`, `partials/galaxy.html`), `static/` (`timemachine.js`, a new `timemachine.css` with the TM
  rules cut from `app.css`), `locale/pl.py` (TM strings cut from `pl_ui.py`), `tests/` ← `tests/test_timemachine.py`,
  `MODULE.md`). Use `git mv` so history follows.
  - **Galaxy partial:** the base's sidebar and the PDF mark also use it, so keep a copy in the base as the job
    mark, and let the module own its own copy.
- [x] **4.7 Storage move:** `data/timemachine/` → `<storage>/modules/timemachine/`, on first start. Copy, verify
  (including `git fsck` of its history), switch, and rename the old one to `*.migrated-<date>`.
  - *Check:* a test on a fixture TM folder with history; `See history` still lists the old commits.
- [x] **4.8 Kept jobs in the v1 job format.**
  - New entries are stored like `<storage>/jobs/<id>/` (`job.json`, `out/`, `inputs/`, `tables/`) plus
    `entry.json`.
  - Old entries are read through `jobformat.read_job`.
  - Adding from Jobs & results copies the job folder through `ctx.jobs`.
  - Retrieval goes through `ctx.backups` (already true after P3.7).
- [x] **4.9 Time Machine backs itself up.** When a backup folder is set, write `<backup>/Time Machine/`:
  - each entry in the v1 backup format (P3 writer);
  - `projects.md`;
  - `timemachine.bundle` (`git bundle create --all`), debounced to at most once per 10 min after a change;
  - `index.json`.

  Add **Restore Time Machine from backup** to the module's System panel.
  *Check:* a test that wipes the TM folder, restores it, and gets the same entries and history.
- [x] **4.10 The boundary check.** Add a test that fails if `mister_plis/` imports `modules` or mentions
  `timemachine`/`/api/tm` outside the migration code (one allow-list file).

## Done when

- with `modules = []`, the app starts, all base tests pass, and there is no Time Machine link, button or filter;
- with `["timemachine"]`, all TM tests pass from `modules/timemachine/tests/` and the whole suite is green;
- the screenshots match the "before" set;
- the migration works on a copy of the real TM folder;
- `docs/MODULES.md` has a first version, written from this phase, describing the interface with Time Machine as
  the example.

## Rollback

Switch to the previous release branch. The old `data/timemachine.migrated-<date>` is still there: rename it
back. Entries added after the move are in the new folder, and the TM backup can restore them.
